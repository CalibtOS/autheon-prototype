## 1. What AUTHEON is (one paragraph — do not re-explain this to the reader)

AUTHEON is a **vehicle-transport / vehicle-relocation dispatch platform (Version 1)**. It replaces a manual, Excel-and-email dispatch process. Admins/dispatchers create **transport orders (tours)** that move a vehicle from a **pickup** location to a separate **delivery** location. Tours reach drivers two ways: the **marketplace** (drivers self-accept published jobs) or **direct assignment** (admin assigns a specific driver). Acceptance is **binding**. Drivers use a **PWA**; admins use a web backend. V1 hands navigation to external map apps (no internal GPS), uses push notifications for drivers (no workflow emails to drivers), and email alerts for admins. The client does **not** want the product named "AUTHEON" in the final UI (display name is configurable).

- **Platform type:** vehicle transport / relocation operations platform
- **Primary users:** Admin / Dispatcher · Driver
- **Core object:** transport order / tour / official transport-order PDF
- **Prototype:** `prototype/project` (single-page HTML/React demo) is the **UI/UX source of truth**; canonical spec is `prd.json`.

## 3. Product vocabulary (shared language — use these exact terms)

**The two job flows**
- **Marketplace flow:** Draft → Published → Accepted → Performed.
- **Direct assignment flow:** Draft → Assigned → Performed.
- Published and Assigned are **mutually exclusive** in Phase 1. A Published job must be reverted to **Draft** before it can be reassigned or direct-assigned.

**Operational job statuses (extended enum, v2.4; special_case removed v2.6):** Draft · Published · Accepted · Assigned · Performed, plus the Storno statuses **`cancelled_by_sp`** (cancelled by service partner) · **`cancelled_by_autheon`** (cancelled by Autheon/admin) · **`empty_run_reported`** (pending admin review) · **`empty_run_recognised`** (terminal) · **`empty_run_not_recognised`** (terminal). `cancelled` is the **only** legacy umbrella (the former `special_case` status was removed in v2.6 — the empty-run model replaces it). On the admin board, precise statuses **roll up to umbrella columns** (Cancelled / Empty-run-reported review / Performed) via `statusUmbrella()`, and each row shows the precise status as a **reason chip**.
**Document review statuses:** Missing · Uploaded · Under Review · Accepted · Rejected · Correction Required.
**Settlement states:** Not Started · Pending · Processed · Paid · Needs Clarification · Closed.
**Driver access (two independent binary axes, v2.35 — replaces the old "driver statuses" list):**

- **Operational access:** Enabled · Disabled — marketplace visibility and job eligibility.
- **Account access:** Enabled · Disabled — login.
- **Invite state** (supporting, _not_ a status, never a pill, never a filter): pending · failed · accepted.

`Disabled` operational access is **lenient**: no marketplace, no direct-assign, no reassign, no new acceptance by any path — but the partner **keeps** already-assigned tours and **can still upload documents on them**. There is exactly one disabled state; _how_ a partner became disabled (admin action vs. the automated inactivity sweep, and its `deactivationReason`) is answered by the **audit log and the change notification**, not by the driver management overview. Map any older mention of Active / Blocked / Inactive / Archived / Soft Deleted onto this model — see `docs/decisions/0001-driver-access-two-axis-model.md`.

**Key meanings that meetings keep touching**
- **Performed** = the vehicle transfer is operationally done. It does **not** mean documents/invoices/settlement are complete (those are tracked separately).
- **Service partner (SP)** = the driver-side actor in the cancellation/empty-run copy (Storno-Workflow-1.pdf uses "Servicepartner"). In V1 the SP is the individual driver; the structured multi-driver company model is deferred (F-08).
- **Report Problem** (driver) has two paths, **reworked in v2.4** (Storno): **Cancel order** and **Report empty run** (Leerfahrt). Both open behind a ⚠ warning entry, need a reason + **≥30-char** text, and use slide-to-confirm. Both are available on **booked** orders only.
  - **Cancel order** → `cancelled_by_sp`; binding-cost warning + T&C link first; **4 reasons** (appointment can't be met, order booked accidentally, execution organisationally impossible, other); order becomes read-only, leaves the active list but is kept in history; admin notified; audited. No auto-republish, no fee processing.
  - **Report empty run** → `empty_run_reported` (locked for the partner, pending review); **6 reasons** (vehicle technically not operational, not roadworthy, not present at pickup, not being released, key/documents missing, other) + optional (never-required) evidence + review/no-guarantee/phone-dispatch warning; admin notified; audited.
- **Empty-run replaces the old "Not Performable → Special Case" path (special case removed entirely in v2.6).** Admin **review** decides **Recognised** (`empty_run_recognised`) or **Not recognised** (`empty_run_not_recognised`) — both terminal, both push/in-app notify the partner; **not-recognised does not reactivate the order**. Map any meeting mention of "not performable" or "special case" to this empty-run workflow. There are no Continue / Republish / administrative-close resolution actions — the review has exactly two outcomes.
- **Acceptance is binding.** Assigned jobs cannot be directly rejected by the driver.
- **Probation acceptance limit** (v1.9, replaces the old per-day quota): a new driver may book up to **N initial jobs (default 3)** and must reach **N Performed jobs** before being **released**; after release there is no further V1 booking limit. It blocks **self-accept only** — admin **direct assignment is exempt** (admin may assign extra jobs even while the driver is on probation). Performed jobs count toward release whether self-accepted or admin-assigned. No rolling daily quota and no driver limit-increase request. Admin may **manually release** a driver from probation. **UI (v2.0):** a probation status/progress card — **not** a limit meter or "request higher limit" action — shown while on probation and **hidden after release**.
- **Driver ID** (v2.0) = **system-assigned, immutable, never reused** (a monotonic sequence; retired or disabled IDs are not reassigned). Assigned automatically at creation, **not** entered by admin. Exact format (prefix/padding/year/start) is client-defined (OQ-16).
- **Time windows** (v2.0) = **same-day per leg** (window start/end on one calendar day; **no cross-midnight**). Pickup and delivery legs may still fall on **different dates**.
- **Vehicle domain** (v2.8, client confirmation “Systemlogik Fahrzeugeingabe”, supersedes the v2.1 “important vehicle info” model) = **four explicit semantic categories** plus independent characteristics. **Never** one unstructured multi-select tag collection — that proposal was rejected. Use these exact terms:
  - **Vehicle type** — *exactly one*: `passenger_car` (PKW) · `truck_up_to_7_5_t` (LKW bis einschließlich 7,5 t) · `truck_over_7_5_t` (LKW über 7,5 t).
    **Removed values** (not selectable for new records): SUV · Van / Transporter · Classic car / Oldtimer · the older `LKW < 3,5t` / `Light truck <3.5t` band.
  - **Vehicle data** — **manufacturer** (dropdown from the manufacturer catalogue) · **model** (separate field) · **official licence plate** (separate field, of the *transported vehicle*) · **VIN** (exactly 17 characters).
  - **Transport type** — *exactly one*: `own_axle` (Eigenachse) · `third_party_axle` (Fremdachse). **This renames the old “Axle” concept — say “transport type”, not “axle type”.**
  - **Registration status** — *exactly one*: `registered` (Zugelassen) · `deregistered` (Abgemeldet). **Independent of transport type**, never inferred from it.
  - **Additional vehicle characteristics** — *independent booleans*: `electric_vehicle` (E-Fahrzeug) · `ready_to_drive` (Fahrbereit). Ready-to-drive is decision-relevant for third-party-axle transport, is not mandatory, and is never auto-cleared. Both are shown to the service partner in the complete order view.
- **Red licence plates** (v2.8) = a **DERIVED** requirement, never a manual selection and **never a recorded plate number**. Partners bring their own red plates; the number is irrelevant to order creation.
  `requiresRedLicencePlates = (registrationStatus === deregistered AND transportType === own_axle)` — the only true case in a four-case matrix (registered+own ✗ · registered+third-party ✗ · **deregistered+own ✓** · deregistered+third-party ✗).
  One canonical backend domain policy owns the rule; the notice “**Rote Kennzeichen erforderlich**” comes from i18n and must appear in **five** surfaces: Admin Backend · marketplace order card · marketplace preview · booking dialog (highlighted) · complete order view **after booking** (it stays visible — it is an execution requirement, not a marketplace message).
  **Removed in v2.8:** the manual “Red licence plates” option, the red-plate-number input, and the rule that hid/cleared the official licence plate when the vehicle was deregistered.
- **Account & sign-in** (v2.3) = the driver's **email is a self-service credential**, not ops-managed master data. Changed via a driver-owned "Account & sign-in" card with a **6-digit code sent to the new address** (verify, don't approve): the new address only goes live after the code is confirmed, the **old address stays live until then** and is notified on success. At most one pending change per account; no ops approval step.

City, postal code, street, country, map actions, dates, time windows, navigation and **contacts** (`contactPerson`, a separate field) are unchanged, and the line is unlabelled data so **no i18n key was added**. **No data-model change.** Open: whether the name should also appear on the transport-order PDF and in My-orders cards.
- **Full date and time in Infopoint metadata** (v2.27, refines Task 18): Infopoint **message** and **document** date lines show the full calendar date plus 24h time as **`DD.MM.YYYY + HH:MM`** (e.g. `30.07.2026 + 13:05`), the `+` being a **literal visible separator** exactly as the work order writes it in both its pattern and its example. Exactly three surfaces: message list row, message detail page, document list row — the document **preview** shows no date and is untouched, and no other date in the application changed. Fields are unchanged (`publishedAt`, `updatedAt`) and both already carry a **real time**, so no time is fabricated; the **year** is missing from the prototype's `nowStamp()` format and is supplied by the formatter's pre-existing `ASSUMED_YEAR = 2026` convention, an artefact of the seed data that disappears once production stores real timestamps. All three sites moved off raw string interpolation onto one shared `formatDateTime`, honouring the formatter module's "no ad hoc date strings in JSX" contract. It assembles from parsed calendar **parts** and never builds a `Date`, so **no timezone conversion can shift the displayed day** (`31.12. 23:59` cannot roll to `01.01.`); a date-only value renders as the date alone rather than a fake `00:00`, and missing/malformed values render an em dash without echoing the raw value. Metadata steps 14px → 12.5px so the longer stamp sits below rather than level with the 14px row title. **Sorting is insertion order and never parsed from these strings**, so ordering, read/unread state, unread badges, navigation, preview/download/share/print, audit logging and visibility rules are all unchanged; the pattern is numeric and identical in EN and DE, so no i18n key was added. **No data-model change.** Open: whether the literal `+` is the intended production separator, and whether the same stamp should replace the remaining relative/short dates elsewhere in the driver app.
- **Driver success checkmark refined** (v2.26, refines the v2.23 dialog standard): the driver success icon is a **standalone gradient mark with no circle or disc** — a 56px checkmark (up from 26px) in an 80px box, its stroke painted by a green→lighter-green gradient over a soft edgeless radial bloom. Applied to **all three** driver success surfaces (tour booked, report-problem/empty-run/SP-cancel, mark-performed), confirmed system-wide rather than local to the referenced screen; the mark-performed stage's **duplicate** SVG, filled disc and 8px ring are gone, so one shared `DialogSuccessIcon` serves them all. **Warning and destructive keep their 52px discs** — a small `!` or `×` reads as an alert only inside a container, so this is a success-only deviation, not the disc standard being retired. A narrowly scoped token family (`--success-mark-*`, `--success-glow*`) was added instead of reusing **or** re-toning `--st-accepted`, whose `#059669` keeps painting every Accepted pill, badge and label. Where the work order's prose and the approved reference image disagreed, the **image won**: there is no black in the mark (so no "black-to-green"), and the reference's bloom was kept despite the "no background containers" wording. Copy, workflow, status transitions, actions, dismissal, the slide-to-confirm gesture and the glyph's decorative `aria-hidden` semantics are unchanged; Admin Backend is untouched. **No data-model change.** Open: client sign-off on the sampled gradient values, and whether the mark should also replace the `✓` glyph in the change-email confirmation.
- **Marketplace empty states split by filter state** (v2.22, refines Task 7): the Marketplace no longer shows a filter-related empty state when **no filter is active**. Two states, chosen from the **same** canonical applied-filter count that drives the filter badge and chip row: filters active + nothing matching → the existing filter-related state **unchanged**; no filters + no open orders → a general *"There are currently no open orders."* message that does not mention or imply filtering and offers **no** filter action. Apply / change / clear / reset switch between them automatically. Previously the filter message showed unconditionally, so an empty marketplace wrongly told the driver their filters were hiding available work. **No data-model change.** Open: approved wording for the general message, and whether driver-facing Marketplace copy should settle on "orders" or "tours" (the existing strings mix them and were deliberately left untouched).
- **Infopoint message detail page** (v2.21, refines Task 18): Infopoint messages **no longer expand** in the list. A list row carries **title + date + read state only** (unread dot + `NEW` badge + the state in the row's accessible name; a read row carries no badge) — the 100-character preview and the expandable body are gone. Selecting a message opens a **dedicated detail page** that replaces the Infopoint header and tab band, showing title, date and the **complete** body with preserved paragraph breaks, never truncated — because a long announcement (updated **AGB**, standing instructions) is unreadable inside an accordion in a scrolling list. **Back arrow upper-left** (shared driver drill-down header, 44px, focus moves to the heading) returns to the complete list with the News tab still selected. Opening marks the message read immediately, the list reflects it on return, and the open is audited as a message view. An **optional left-edge swipe-back** is implemented as progressive enhancement and never replaces the visible back arrow. v2.20's message deep links (notification tap, Infopoint push) land here. Admin publishing, the unread tab badge, newest-first sort and the Documents/Help tabs are unchanged. **No data-model change.** Open: iOS-only vs every touch platform for the gesture.
- **Type-aware driver notification previews and deep links** (v2.20, refines Task 20): every Notification Center card shows a **category** chip (Order · Account · System · General information), a meaningful heading, preview text capped at **two lines**, date/time and read/unread. **Two interaction models only** — tour events (new matching Marketplace order, order updated after booking, cancelled by Autheon, empty-run outcomes) get an **inline expandable preview** with the control on the right and one contextual action (*View order* → Marketplace preview, *To my orders* → full detail); Infopoint messages and document outcomes **deep-link to that exact message/document** and never render the accordion. **No universal bottom sheet.** The expanded preview follows `driver_visibility_matrix` by OMITTING customer, full addresses, contacts, plate and VIN from the payload for an order the driver has not committed to — not by hiding them. A Marketplace order since booked, withdrawn or cancelled is labelled with the reason, loses *View order*, permits no acceptance, and offers *View more orders*. Navigation resolves through **stable entity ids**, never display text. **Push taps** use the same resolver (`?notify=<id>`): tour → its card already expanded, Infopoint → the message, document → the document; never the generic overview; safe fallback for missing/expired/unauthorized targets; works cold-start, backgrounded and already-open (delivery still simulated). Open: final category taxonomy, approved card visuals, profile-decision deep-link destination, whether profile-approval/document-acceptance gain push, and whether *View more orders* should be conditional.

## 9. Key global business rules (the ones meetings most often touch)

- One job = **either** marketplace **or** direct-assignment flow (not both).
- Admin may revert **Published → Draft** directly (removes from marketplace, enables edit/re-publish/assign).
- Admin may **permanently delete Draft only**; other statuses use cancel/revert/empty-run review.
- Driver **acceptance is atomic** — only one driver can accept a Published job.
- Before acceptance, marketplace shows **reduced data** (rough region, distance, dates/windows, vehicle type, manufacturer/model, **transport type**, registration status, additional characteristics, the derived red-licence-plate notice where it applies, offer/price). Official licence plate and VIN stay hidden until acceptance/assignment; full detail only after acceptance/assignment.
- **Marketplace filter control shows an applied-filter count** (v2.9): a numeric badge on the filter button states how many filters are currently narrowing the list, so a constrained — or empty — result set is explained even with the filter panel closed. Semantics: the count is derived from **active filter state**, never from the number of matching orders; a filter counts only when it restricts results (postal-code fields when non-empty; **each** bound of a date range separately; vehicle/axle only when not the `All` default; empty/whitespace/null/undefined/default never count; each filter at most once). **Sorting is excluded** and the sort control carries no badge; free-text search is not a filter. The count reflects **committed** filters — draft selections in the open panel do not move it until applied, and Cancel discards them. **Zero applied filters renders no badge at all** (no "0", no reserved space). It updates on apply / remove-one / clear-all, stays correct while the panel is closed, and persists exactly as Marketplace filter state does (session-scoped: survives tab navigation, resets on reload — no persistence was added for the indicator). Accessibility: the count is announced via a translated, **pluralized** accessible name ("Filters, 3 applied" / "Filter, 3 aktiv"), the badge is decorative and not separately focusable, and the control stays one target with a visible focus ring and adequate touch size. Responsive: one layout for phone and tablet widths, badge stays attached and never shifts the surrounding controls. **No data-model change** — pure frontend derived state. *(Open defect: the `This week` date preset is counted but the filter predicate does not implement it — see PRD changelog 2026-07-27 §3.)*
- After acceptance, a driver **cannot casually return** a tour — must use **Report Problem** → **Cancel order** (`cancelled_by_sp`) or **Report empty run** (`empty_run_reported`). Both booked-only, ⚠-gated, ≥30-char reason, slide-to-confirm (v2.4). *(Residual phase-gating question — see OQ-17.)*
- **Empty run → admin review → Recognised / Not recognised** (both terminal); not-recognised does **not** reactivate the order. This supersedes the old "Not Performable → Special Case" routing; the `special_case` status was **removed in v2.6** (`cancelled` is the only remaining legacy umbrella).
- **Two cancellation actors:** the **service partner** cancels (`cancelled_by_sp`, no auto-republish, no fee processing) or **Autheon/admin** cancels (`cancelled_by_autheon`); admin cancel of a **booked** order notifies the partner and honours the cutoff policy, **unbooked** cancels are immediate. Orders are never deleted — cancelled tours are read-only and kept in history.
- **Admin can edit ALL eligible business data on any non-terminal order** (draft, published, assigned, accepted, empty_run_reported) through the canonical Create/Edit Job form — including already-booked orders (Storno §7). Terminal orders (cancelled_by_sp/cancelled_by_autheon/empty_run_recognised/empty_run_not_recognised/performed) are permanently read-only. Editing business data does **not** require reverting a Published order to Draft; the operational status is preserved. On save the assigned partner is notified with the **actual driver-visible changed values** in one combined notification (internal notes / admin-only financials excluded), the audit stores previous→new per field, and no re-confirmation is required. Edit eligibility lives in one `canAdminEditOrder()` policy. **Duplicate order** creates a new draft with a new order number (not in marketplace until Publish); it is the only way to reuse a terminal/cancelled order. **`empty_run_recognised` is a terminal empty-run resolution, NOT a performed transport** — it never counts toward probation release or performed-job logic; `statusUmbrella()` board grouping is presentation-only and never drives workflow logic.
- **Internal admin notes** (v2.4): admin-only, timestamped, permanent; never shown to the driver.
- **Performed ≠ documents/settlement complete.** Document review + settlement are separate state machines.
- **The camera never opens until the driver explicitly picks the photo action.** Every Driver PWA document-upload control (tour-completion success modal, tour-detail **Tour documents** card incl. *Replace file*, performed-tour **Meine Dokumente** tab) routes through one shared upload-source component: document type → source choice → device. *Take photo* uses a capture-enabled input restricted to the supported image types; *Choose file* uses a plain OS picker with `application/pdf` + the supported image types and **no** capture attribute. Backend validation is MIME-first with an extension fallback (never extension alone), enforces the 25 MB ceiling on every upload path, and applies image processing only to actual images — a PDF is stored and shown as a document, never fed to a thumbnail/image pipeline. Client-side checks are never the only protection.
- Drivers get **no workflow emails**; PWA + push only (⚠️ an optional post-booking driver email is **under decision** — see OQ-14; rule unchanged until then). **Transactional account emails do exist** (v2.3 email-change code + old-inbox security notice) — these are account-security, not workflow, so they don't conflict with OQ-14. Admins get **email alerts** for critical events.
- System must **preserve manual admin control** for edge cases — never hard-block operations just because a rare flow wasn't predicted.
- V1 = **simple A→B only**; chains represented as separate orders.
- Cancellation records **actor** (driver / admin / customer), reason code, optional text, timestamp, user.
- Every operational transition writes **status history** (prev, new, time, user, comment, evidence ref).
